# 後端改用 Python：交付說明

日期 2026-11-04，2026-11-05 更新。給老師與組員看：做了什麼、怎麼證明它和原本的 TypeScript 後端一致、哪些還沒做、怎麼跑起來。逐項的細節在 [backend-python-remaining.md](backend-python-remaining.md)，總計畫在 [backend-python-plan.md](backend-python-plan.md)。

## 一句話

原本的 TypeScript 後端（AIHOT）已經**全部用 Python（FastAPI + psycopg）重寫，並且每一塊都拿 Node 版逐項比對過**。需要付費模型、飛書、X、公眾號、Jina 的部分，是用本機的假服務（假模型、假機器人、假 API）跟 Node 版比對的；**真實服務、真實金鑰那一側還沒驗證**（見下面「還沒驗證」）。前端（`apps/web`）不動，照舊透過 `API_BASE_URL` 讀後端。

## 驗證的原則

「改寫完」不等於「正確」，所以每一塊都用同一個辦法證明：**同一份輸入，Node 版和 Python 版各做一次，比對結果。**

| 類型 | 做法 | 例子 |
|---|---|---|
| 讀取端 | 兩個伺服器連同一份資料庫，送同樣的請求，比對狀態碼、重要標頭和 JSON | 公開 API、RSS、網站頁面 |
| 會寫資料的功能 | 把資料庫複製成兩份，Node 與 Python 各處理一份，最後逐列比對資料表 | 發布、熱度排行、文章入庫、後臺所有動作、收集一個信源 |
| 抓網站的功能 | 本機架假網站，兩邊各抓一次，比對解析結果 | RSS、JSON 列表、網頁列表 |
| 純函式 | 由 Node 對大量輸入產生答案，Python 逐一比對 | 日期解析 269 組、過濾與設定檢查 119 組、請求驗證訊息 57 組 |
| 正文擷取 | 同一批網頁交給兩邊的 Readability 讀，比對輸出 | 27 頁手寫版型 + 2,000 頁隨機組合，另外 30 篇真實網站文章全部相同 |

目前測試套件共 **1,422 個測試，全部通過**（`tests/` 底下的 unit、engine、integration、parity）。

### 2026-11-05 補充：前端實際對照

- `tests/parity` 的 **422 個對照測試重跑一次，全部通過**（8 分 20 秒，用 `seeded` 資料庫）。
- 同一個前端（`apps/web`）分別接 Python 版與 Node 版 API，兩邊用同一份資料庫，逐頁比對回傳的 HTML：
  - 前台 22 個頁面一致：首頁、9 篇文章頁、3 個事件頁、`/rss.xml`、`/feed.xml`、`/sitemap.xml`、`/robots.txt`、`/hot`、`/weekly`、`/about`、`/admin/login`，以及兩個兩邊都回 404 的頁面（`/search`、`/events`）。
  - 後臺登入後 13 個頁面一致：總覽、內容、信源（列表、新增、3 個詳情頁）、回饋、執行紀錄、模型、SelectBench、設定、稽核。
  - 唯一的差異是網址寫法（`localhost` 與 `127.0.0.1`），來自本機啟動前端的方式，與後端無關。
- **切換前一定要先跑 `newsroom migrate`。** 只跑過 Node 遷移的資料庫沒有 `job_schedules` 資料表，`/api/admin/runs` 會回 500、後臺執行紀錄頁回 503；跑完遷移後與 Node 版一致（只剩「目前執行中的程序」與檢查時間不同，這兩項本來就不會一樣）。
- 後臺的寫入操作也經前端比對過：前端的後臺頁面本身不寫資料，寫入是瀏覽器帶著登入 cookie、CSRF 令牌與 Idempotency-Key 送到 `/api/admin/*`，由前端伺服器轉給 API。用同樣的請求分別送進接 Python 與接 Node 的前端（各連自己的資料庫複本），22 筆寫入（內容可見度、SEO、欄位覆寫、回饋封禁、通知目標、預算、信源暫停與過期版本，含被拒絕的、過期版本與缺 CSRF 令牌的情形）的狀態碼與回應內容全部一致，留下的資料列（人工覆寫、公開列、通知目標、信源、稽核紀錄）也一致。
- 沒有做的：沒有人工肉眼對照畫面；會呼叫外部的寫入（立即收集、預覽、重跑）沒有經前端比對，只靠 API 層的對照測試。

## 還沒驗證（程式都寫好了，缺的是真實服務）

上面列的功能全部有 Python 版，也都用本機假服務跟 Node 版逐項比對過。下面這些只有拿到真實金鑰或環境才能證明：

| 項目 | 缺什麼 |
|---|---|
| 分析、評分、翻譯、事件歸組、綜述、週報月報的**輸出品質** | 用假模型只能證明提示詞組裝、結果解析、寫入與重試和 Node 一致。真實模型只用本機 `qwen2.5:14b` 測過判斷相關、評分、理解三步（18 篇）；翻譯、歸組、綜述、日報週報沒用真實模型跑過；雲端模型沒測 |
| 飛書：應用那一側（換取憑證、傳圖、發到聊天室）與飛書登入的真實流程 | 真實飛書。Node 的網址寫死，沒辦法指向假伺服器；Python 版照原版的請求格式寫成，沒有實際連過飛書 |
| X 搜尋、公眾號、Jina | 真實的 SocialData、Dajiala、Jina 服務與金鑰 |
| 備份上傳到真實雲端服務 | 備份上傳已在本機用 S3 相容儲存（SeaweedFS、HTTPS、SigV4 簽章）實測過：Python 與 Node 各上傳一份，下載後 `pg_restore` 讀得出；雲端服務（COS、S3）本身沒有真實帳號可測 |
| 大量真實資料與長時間運作 | 對照都用造出來的資料；壓力測試只做了粗測（40 篇與複製出來的 5 萬篇，50 與 200 個併發，兩邊都沒有錯誤）；真實的大量資料、幾十萬篇以上、長時間運作沒測 |

## 已知的限制與風險

1. **佇列不互通。** Python 用自己的資料表（migration 0123），不與 Node 的 pg-boss 互通。切換時整個引擎要一起換，Node 佇列裡還沒處理的工作不會帶過去。
2. **正文擷取靠樣本驗證。** 2,000 頁是產生的、30 篇是真實的，全部一致；2026-11-05 又抽了 74 個真實頁面（43 個來源：簡體與繁體中文新聞站、英文媒體、日文、論壇、技術部落格、文件、維基、arXiv、GitHub，以及會擋爬蟲的站與首頁／列表頁）讓 Node 與 Python 各讀一遍，逐項比對（正文 HTML、純文字、圖片、讀法、發布時間）。第一次 73 個一致、1 個不同（MDN）：Node 的 Readability 用 `querySelectorAll` 找要刪的 `<style>`，而 linkedom 的它不會進入 `<template>`（網頁用 declarative shadow DOM 時，裡面的 CSS 會留著，並算進外層元素的文字量，影響評分），Python 版沒有這個差異。已修正（`_getAllNodesWithTag` 不進入 `<template>`），加了一個回歸測試（舊程式碼下失敗、修正後通過），重比 74 個全部一致（其中 9 個兩邊都讀不出文章，如知乎、微信、Reddit 的擋爬蟲頁）。仍然是抽樣：樣本是當天各站首頁 RSS 的前兩篇，沒有涵蓋特別少見的版型。
3. **圖片像素不同。** 圖片縮放與分享圖改用 Pillow，格式、尺寸、快取鍵與標頭一致，但像素不會與 sharp／satori 完全相同。
4. **日期範圍。** Python 的日期最多到西元 9999 年；單位填錯造成的超大日期，Node 會算成遠古年份，Python 當作「時間未知」。
5. **沒有模型金鑰就不會分析。** 分析工作由 Python 工作行程處理，但沒有金鑰（或 `MODEL_CALLS_ENABLED` 關著）時，文章會停在「待分析」。

## 怎麼跑

需求：Python 3.12、PostgreSQL。

```
pip install -e ".[dev]"   # 依賴已列在 pyproject.toml
newsroom migrate                      # 建立資料表（含工作佇列）
uvicorn --factory newsroom.api.app:build_app --port 3001   # API
newsroom worker                       # 工作行程：收集、抓正文、排程、心跳
```

環境變數沿用原本的（`DATABASE_URL`、`ADMIN_PASSWORD`、`API_PORT` 等）。

**用本機模型（Ollama）代替雲端模型：** 程式向 `LLM_BASE_URL` 發標準的 OpenAI 格式請求，所以任何 OpenAI 相容的本機伺服器都能接。在 `AIHOT/.env` 設 `LLM_BASE_URL=http://127.0.0.1:11434/v1`、`LLM_API_KEY=ollama`（隨便一個非空字串）、`LLM_MODEL=模型名`、`LLM_EXTRA_JSON={}`，再用 `python start_dev.py --models`。本機模型常常不照提示詞的規則填值（自己編一個分類、把分數寫成 0 到 1 的小數），答案會被檢查擋下。所以 `start_dev.py` 在 `--models` 且模型網址是本機時，自動打開 `LLM_STRUCTURED_OUTPUT=true`：判斷相關、評分、理解這三步改用 `json_schema` 把可填的值直接交給伺服器限制（`engine/structured.py`），預設關著，雲端模型不受影響，和 Node 版的對照也不變。2026-11-05 在 RTX 5080（16GB）上用 `qwen2.5:14b` 實測 3 個信源：不用限制時 16 篇有 5 篇被擋（分類填「article」「文章」、分數填 0.85）；打開限制後 16 篇全部分析成功，每篇約 8 秒。品質（評分偏低、有些中文標題用簡體字）還需要更多樣本判斷，也沒有和別的模型比較過。

**用 Docker 跑整個 Python 後端**（網站前端維持原樣）：

```
docker compose -f AIHOT/docker-compose.yml -f deploy/python-backend.yml up -d --build
```

`setup` 執行 `newsroom migrate`（空資料庫一個指令建完 86 個遷移），API 與 worker 都用 Python，網站前端照舊在 3000。不要再疊 `deploy/newsroom.yml`，worker 自己跑收集與抓取排程。2026-11-05 在空資料庫上實際跑過一次：遷移成功、API、worker、前端都起來，首頁、文章、RSS、sitemap、`llms.txt`、圖片、後臺登入與各後臺頁面都回 200，worker 有程序心跳，映像內有 `pg_dump` 17。第一次跑發現並修掉兩個只有容器裡才有的問題：安裝後的套件找不到 `AIHOT/` 資料夾（遷移檔、靜態檔、字型），改用 `AIHOT_ROOT` 指定；映像沒有 PostgreSQL 客戶端，備份會失敗。之後又在容器裡打開收集（模型呼叫仍關著）跑了一次真實收集：用後臺 API 建了 3 個真實公開 RSS 信源，worker 的排程把它們排進佇列、抓取、過濾、入庫，53 篇文章全部抓到正文，53 個分析工作排進佇列（沒有模型，文章停在待分析）。這次發現並修掉一個只有真實執行才會出現的問題：處理函式的結果裡若有日期（分析在等模型時會回傳下次重試時間），寫進佇列結果欄位會因日期不能轉成 JSON 而失敗，工作就一直停在進行中；現在日期與 pg-boss 一樣存成 ISO 字串，並有回歸測試。

Windows 本機開發可以一次全開：先打開 Docker Desktop，再在專案根目錄執行 `python start_dev.py`（資料庫、API、worker、網站各一個視窗，網站在 http://127.0.0.1:3000）。預設用獨立的 `dev` 資料庫（第一次自動建立、建表、放進 33 個預設信源）並打開信源收集，模型呼叫關著；`--no-collect` 不收集，`--models` 打開模型呼叫（會產生費用，金鑰從 `AIHOT/.env` 讀），`--db seeded` 改用測試用的假資料。沒有模型時收集到的文章停在待分析，網站的精選看不到，停止用 `python stop_dev.py`（只停 start_dev.py 開的那幾個視窗；舊的或漏掉的程序用 `python stop_dev.py --scan` 找出來，確認後停掉）。

跑測試：

```
python -m pytest tests -q                          # 單元與引擎測試
PARITY_DATABASE_URL=postgres://…/seeded \
  DATABASE_URL=postgres://…/newsroom_test python -m pytest tests -q   # 加上與 Node 的比對（要 Node 與已種資料的資料庫）
```

比對測試需要 Node 與 `AIHOT/node_modules`，沒有時會自動略過。

## 建議的下一步

1. 用本機模型多跑一段時間（1 到 2 小時、33 個信源全開），看網站的精選、事件、翻譯、日報有沒有產生，品質夠不夠用；不夠再比較 `qwen3.5` 或更大的模型。
2. 切換前：對資料庫執行 `newsroom migrate`，並一起換掉整個引擎（佇列不互通）。
3. 申請免費的 `GITHUB_TOKEN`（預設有 8 個 GitHub 信源，免填會被限流）。
4. 取得雲端模型金鑰後：用真實金鑰小量比對 Node 版的提示詞與結果。
5. 取得飛書憑證後：實際跑一次通知與登入。
6. 確認結果後，單獨一個 commit 刪除 AIHOT 裡的 Node 後端程式。
