## 1. 背景

創作者經營一個繁中 AI 科技資訊帳號，在 Threads、IG（輪播、Reels）、YouTube Shorts 發文。現在每則內容都是手工：滑 X 找題目、開原文、下載 Demo、寫稿、錄音、剪片、上字幕、發布、回頭看數據。最花時間的不是判斷，而是搬運和整理。

對標帳號的分析（05 §2）顯示：題目從第一手公開到發文，中位數約 1 天；大事件會在幾小時內連發 3 支。想追上這個速度，只靠手工做不到。

## 2. 產品目標

讓一個人能把 AI 科技情報，快速做成有來源、帶自己觀點的繁中貼文、輪播或短影音。人把時間花在選題、觀點與錄製；系統負責收集、整理、草稿與製作。

| 目標 | 說明 |
|---|---|
| G1 一則走到底 | 任何一則內容都能從「貼網址」走到「發布並記錄成效」，中間每一步都能看到進度和缺什麼 |
| G2 減少搬運時間 | 收集、補料、草稿、字幕、合成自動化，人只做四件事：選題、改稿、錄製、最後確認 |
| G3 跟上時事 | S 級事件 2 小時內發出輪播；長期目標 6 小時內出 Reel |
| G4 可追溯 | 成品裡的每個數字與說法都能回查到原文；每個素材都能回查到來源網址 |
| G5 不出事 | 人沒確認的東西不會被發出去；人改過的稿不會被程式蓋掉 |

## 3. 非目標

- 多人協作、權限、審批流程（使用者只有創作者本人）。
- Web 後台。介面就是資料夾、Markdown 和 Obsidian，入口是 CLI 與 Claude Code slash command。
- 自寫 IG／Threads 爬蟲（封號風險高）。
- 全自動「無人值守」發文。即使 S6 接上自動發布，發布前仍需要人確認。
- 對外販售或服務其他創作者。

## 5. 成功指標

| 指標 | 量法 | 第一版（R3，S5 結束） | 完整版（R6，S7 結束） |
|---|---|---|---|
| 一則 Threads 從選題到可發布 | Job 時間戳＋人工計時 | ≤ 30 分鐘 | ≤ 15 分鐘 |
| 一則輪播從選題到可發布 | 同上 | ≤ 90 分鐘 | ≤ 45 分鐘 |
| 一則 60 秒 Reel 從錄完旁白到成品 | 同上 | ≤ 30 分鐘（機器時間） | ≤ 15 分鐘 |
| 每天花在找題目與整理的時間 | 創作者每日自填 | ≤ 20 分鐘 | ≤ 10 分鐘 |
| S 級事件到第一則輪播發出 | 首次出現時間 → 發布時間 | 不設門檻 | ≤ 2 小時 |
| 草稿中無來源的數字 | review 時的待確認項數 | 全部被標出 | 全部被標出 |
| 人工稿被覆蓋事件 | 版本紀錄稽核 | 0 | 0 |
| 每週產出 | 已發布 Publication 數 | ≥ 5 則 | ≥ 10 則 |

量測基準：開工前（Week 0）創作者先手工發幾則，記錄每一步耗時，作為對照組。

## 6. 範圍與發布分期

一個 Sprint 為兩週，共 7 個 Sprint（14 週；排程依據見 [分工與 DAG §1](../process/team-dag-sprint.md#1-為什麼是-7-個-sprint)）。每個 Release 結束時，至少要有一則真實題目跑完該期範圍。

| Release | Sprint | 使用者可以做到 | 對應 |
|---|---|---|---|
| R1 | S1–S2 | 貼網址 → 看 inbox → 選題 → 自動抓原文 → 出草稿 → 改稿 → 輸出 Threads 文字 → 確認 → 手動發布 → 填回網址 | 06 批次 1 |
| R2 | S3 | inbox 每天自動從 RSS、GitHub、HN、Reddit 更新；自動下載官方影片與圖片；做輪播圖；手填成效、看週報 | 06 批次 2 |
| R3 | S4–S5 | 放進自己錄的旁白，自動對時出繁中字幕，套固定模板輸出 Reel；改了稿或素材會提示需要重製 | 06 批次 3 |
| R4 | S4–S5 | X List 與書籤自動進 inbox；同一事件自動歸成一題，並給 S／A／B 熱度等級；發表會行事曆；S 級事件推播到手機；IG／Threads 成效自動回收 | 05 §5、§7、§11 |
| R5 | S6 | Reel 有 2D 動態、Demo 包裝、程式碼動畫；沒有 RSS 的頁面也能監測變動；抓不到的 Demo 自動開瀏覽器錄影；S 級事件自動排出連發計畫 | 05 §6、§9 |
| R6 | S7 | 確認後由系統排程發布到各平台；3D 與 AI 影片段落；一題三波；週檢討直接提出門檻調整建議 | 05 §9、§11 |

## 8. 使用者流程

完整流程見 [06 §4](../archive/06_Content_Pipeline_MVP_Handoff.md)。PRD 只強調三個原則：

1. **日常主線**：開 inbox → 選題、寫角度 → 補資料 → 改稿 → 製作 → 看預覽 → 確認 → 發布 → 記錄效果。
2. **修改回路**：缺資料就回去補料；觀點不對就回去改稿；字幕或畫面有問題就回去製作。每次改動後都要重新看成品、重新確認。
3. **打勾只代表選題，不代表允許發布。** 發布一定要有明確的確認動作，而且確認綁定某一個成品版本。

## 9. 非功能需求摘要

細節見 [SRS 00 §6](../spec/00_overview.md#6-非功能需求)。

| 類別 | 要求 |
|---|---|
| 可靠 | 任一步失敗不影響其他步；成功的輸出保留；可單步重跑 |
| 資料安全 | 人工稿永不被程式覆蓋；原始素材唯讀；金鑰只放環境變數 |
| 可追溯 | 成品 → 素材 → 來源，全程有 ID 對照 |
| 成本 | 外部 API 都有每日／每月花費上限，超過就暫停並通知 |
| 可替換 | 外部工具都包成 adapter，換工具不動流程 |
| 環境 | 單機 Windows＋WSL；外部服務一律用 Docker；Python 用 poetry，Node 用 nvm |

## 10. 假設與限制

- 只有一台機器、一個使用者；不需要高可用。
- GPU（3090）是否可用尚未確認（05 §13）。確認前，ASR 與渲染以 CPU 為準，AI 影片走雲端。
- X、Threads、IG 的 API 價格與額度可能變動，接入前一定要做 Spike 驗證。
- 素材版權：發布就是公開散布。系統要能標示素材來源與用途，但是否使用由人決定。

## 11. 決策紀錄

| # | 議題 | 決定 | 原因 |
|---|---|---|---|
| D1 | 05 和 06 衝突時以誰為準 | **以 06 為準** | 06 是較新的收斂版本 |
| D2 | 資料模型 | Topic → 多個 Content → 多個 Publication（06 §7），取代 05 的 `burst_plan` 單一狀態 | 同題多則內容要各自追蹤進度 |
| D3 | 資料夾結構 | 採 06 的 `contents/<content_id>/` 結構；共用素材放在 topic 底下 | 每則作品有自己的稿件與輸出 |
| D4 | 主資料歸屬 | Markdown 是人工內容的主資料；SQLite 是執行紀錄的主資料 | 避免兩邊各存一份可編輯的稿件 |
| D5 | 介面 | 資料夾＋Markdown＋Obsidian＋CLI／slash command，不做 Web 後台 | 單人使用，少一層 |
| D6 | 影片合成層 | Remotion 為主要合成層；HyperFrames（Apache-2.0）列為技術備援，S1 做 Spike 驗證 | 動畫能力強、可程式化；授權見 D14 |
| D7 | 自動錄影 | 不幫每個工具寫腳本，只寫一支通用錄影腳本，排在 R5 | 大部分 Demo 用下載就能取得 |
| D8 | 爬蟲 | 不自寫 IG／Threads 爬蟲；X 先走官方 API，第三方服務只當備援 | 封號與維護風險 |
| D9 | 狀態機 | 沿用 07 的 Content、Job、Publication 三張狀態圖 | 已定義清楚 |
| D10 | 工作流平台 | 自寫 Python 協調器＋SQLite 為主幹；n8n 只在「通知＋核准 UI」真的成為痛點時才加，且不持有流程狀態 | 研究結果：去重、聚類、分層補料都是有狀態的確定性邏輯，Python 較適合；n8n 2.0 起預設關閉 Execute Command，呼叫本機工具不便（見架構文件 ADR-02） |
| D11 | Reddit 來源 | Reddit 公開 API 預計 2027-03 前關閉、RSS 2026-11-13 停止；Reddit 降為選用來源 | 研究結果（見技術選型 §1.3） |
| D12 | 字幕對時 | 自錄旁白有講稿時，用強制對齊（forced alignment）把講稿貼上時間；ASR 只用來比對有沒有念錯 | 講稿已知，對齊比辨識準（見技術選型 §2.2） |
| D13 | 草稿生成 | 拆成「抽事實（開 Citations）」與「寫稿（結構化輸出）」兩次 LLM 呼叫，再加一道程式檢查 | Claude API 的兩個功能不能在同一個請求同時開啟 |
| D14 | 工具授權（2026-10-23） | POC 階段不把授權列入選型考量，Remotion 直接採用；轉商用前重新檢查所有工具授權（Remotion 4 人以上團隊需付費，見技術選型 §6） | 目前是內部 POC，不對外販售；授權問題留到商用前再評估 |

## 12. 風險

| 風險 | 影響 | 對策 |
|---|---|---|
| 平台 API 價格或政策變動 | X 收集、自動發布無法使用 | 每個外部來源都能停用，系統退回手動網址與人工發布 |
| 補料工具因平台改版失效 | 素材抓不到 | 分層備援＋每日自我測試＋人工補料 |
| 三人並行時互相卡住 | 進度延誤 | 契約先行與 fixture，DAG 明確交棒點 |
| 繁中字幕品質不足 | Reel 不能用 | S3 前先做 ASR 與斷詞的 Spike，用真實錄音量測錯誤率 |
| 渲染太慢（沒有 GPU） | Reel 出片慢 | 3D 與 AI 段落延到 R6；先確認 GPU |
| 素材版權爭議 | 帳號風險 | 優先使用官方素材、片段要短、標註來源，在 review 列出待確認的素材用法 |
