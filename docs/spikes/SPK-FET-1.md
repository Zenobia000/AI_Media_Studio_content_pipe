## 1. 做法與必須先說的限制

- **技術選型寫的是 trafilatura＋curl_cffi（Python）**，但專案決定沿用 AIHOT（Node），所以比較的是 AIHOT 現成的 Readability 擷取（`content/extract.ts`），不是 trafilatura。兩者結論不能互換。
- **沒有做人工標註正文**。票面要的「正文完整率」需要人先標出 50 篇的標準正文，這次沒有做，所以**沒有可信的完整率數字**。下面只有能自動量的東西：成功率（正文 ≥ 200 字）、雜訊行比例（關鍵字啟發式，很粗）、日期與 RSS 日期相差不超過一天的比例、耗時。
- **曾經嘗試過「相對最長版本」當完整度，結果是錯的**：Jina 會把導覽列、廣告、相關推薦也算進去。人工檢查 iThome 的一篇（news/180133）：Readability 抓到 910 字，是完整乾淨的正文；Jina 回 16,926 字，是版面加正文，而且正文出現兩次。這個指標已從報告拿掉。
- **Crawl4AI 沒有測**，需要 Python 或 Docker 加瀏覽器，這台機器沒有準備。
- **`run.ts` 抓頁面時用了瀏覽器 User-Agent**，所以表 1 的 Readability 數字是在偽裝 UA 下量到的，**不代表正式系統的成功率**。正式的擷取器（T-023）用 AIHOT 宣告身分的 User-Agent，不偽裝成瀏覽器；表 2 才是它實際的成績。
- 樣本 59 篇，取自本專案自己的信源即時抓的最新文章（`samples.json` 已凍結，可重跑）：官方 blog 與研究 20、英文科技媒體 16、中文媒體 10（iThome、科技新報）、電子報 4、GitHub repo 5、arXiv 論文 4。有偏差：樣本全來自我們自己訂閱的來源，且都是當天新文章。
- 「成功」只代表擷取到至少 200 字，**不代表內容正確、完整**。

## 2. 結果

**表 1：三個方案各自的表現**（Readability 與 Jina 用瀏覽器 UA 抓頁面；Jina 免費額度、無 key）

| 方案 | 成功率 | 雜訊行比例 | 日期正確率（可比對者） | 耗時中位數 |
|---|---|---|---|---|
| A Readability（AIHOT） | 100%（59/59） | 0.0% | 94%（30/32） | 359 ms |
| B Jina Reader | 92%（54/59） | 1.1% | 97%（33/34） | 821 ms（90 百分位 6.4 秒） |
| C 站方 API（GitHub README、arXiv 摘要） | 100%（9/9） | 0.0% | — | 375 ms |

- Jina 的 5 個失敗全是 GitHub 頁面（HTTP 403）：它不讀 github.com。
- 雜訊行比例用關鍵字（cookie、subscribe、訂閱、版權……）數短行，漏抓很多，**只能當粗略參考**。人工抽查發現 Readability 的頭尾仍會留版面文字：The Verge 開頭有 "Skip to main content"、結尾有 "Follow topics and authors"；科技新報結尾有頁尾廣告；TLDR 電子報 11,112 字含贊助廣告與頁尾。這些在關鍵字啟發式裡量不出來。

**表 2：T-023 的擷取器端到端**（誠實 UA、站方 API → Readability，沒有 Jina）

| 類別 | 成功 |
|---|---|
| 官方 blog／研究 | 18/20 |
| 英文科技媒體 | 16/16 |
| 中文媒體 | 10/10 |
| 電子報 | 4/4 |
| GitHub | 5/5 |
| arXiv | 4/4 |
| **全部** | **57/59（96.6%）** |

- 兩個失敗都是 `openai.com`，HTTP 403（網站擋掉宣告身分的爬蟲）。同兩篇在表 1 的偽裝 UA 下 Readability 都成功，Jina 也成功（2,006、8,080 字）。
- 這代表：**誠實 UA 會被一部分網站擋下**。這是系統要面對的實況，不要靠偽裝 UA 解決。

## 3. 結論與建議的擷取順序

1. **有站方介面的就用介面**：GitHub（README 與 release notes）、arXiv（摘要與作者）、YouTube（oEmbed 加說明）。Jina 不讀 GitHub，Readability 對 GitHub 與 arXiv 頁面的結果較不乾淨。
2. **其餘用 Readability**（AIHOT 現成，本機執行、快、免費）。
3. **失敗時用 Jina Reader 備援**（AIHOT 已有，需要 `JINA_API_KEY`，有預算熔斷）。對被擋的官方站（如 openai.com）有救回的紀錄。
4. **還是失敗就 blocked**（`E_MISSING_SOURCE`，結束碼 3），在 notes.md 提示人把原文貼進 `sources/manual-<n>.md`。這是 spec 本來就規定的出口，不是缺陷。

**驗收對照**

| 驗收 | 結果 |
|---|---|
| 每個方案有四項數據 | **部分達成**：成功率、雜訊、日期、耗時有；**正文完整率沒有**（需要人工標註，未做） |
| 套用建議順序覆蓋率 ≥ 95% | 誠實 UA、不含 Jina：96.6%（57/59）。含 Jina 備援預期更高，但**沒有實測**（沒有 key，只有表 1 的兩筆佐證）。標準是「≥ 200 字」，不是人工確認正確 |
| 註明 Jina 授權與費用影響 | 見下 |

## 4. Jina Reader：授權與費用

- 技術選型已記載：免費 token **限非商業用途**。這個專案是內部 POC，但若之後商業使用，需要改用付費方案或換成自架方案（例如 Crawl4AI，尚未評估）。
- 網頁內容會**送到第三方**（`r.jina.ai` 會代為抓取並回傳）。對公開文章影響小；不要送需要登入或內部的網址。
- 本次無 key 的免費額度約每分鐘 20 次，腳本因此每篇間隔 3.5 秒。AIHOT 的整合需要 `JINA_API_KEY`，依 token 計費，已有預算熔斷（`providers/receipts.ts`）。實際費用沒有量測。
- 速度較慢：中位數 0.8 秒，中文媒體約 6 秒。

## 5. 還沒做、建議之後補

1. 人工標註 20 到 50 篇正文，量真正的完整率與雜訊；順便找出 Readability 頭尾殘留版面文字的規律，在後處理中修掉。
2. 評估 Crawl4AI 或其他自架方案，取代需要付費、送第三方的 Jina。
3. 針對被擋的網站（openai.com 等）決定長期做法：Jina 備援（付費）、請人貼原文，或改用該站的 RSS 全文（AIHOT 的 RSS 收集器已可取得部分全文）。
4. 中文網站的日期：樣本中 iThome 與科技新報沒有 RSS 日期可比對（日期正確率 —），沒有驗證。技術選型提醒過「中文網站的日期常抽錯」，這點仍是未驗證。
